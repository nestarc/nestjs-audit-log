# @nestarc/audit-log — v0.2.0 Roadmap

Date: 2026-06-11
Status: Proposed

## Background

0.1.0 출시 후 코드베이스 전수 조사(코어 아키텍처 / 스토리지·SQL 계층 / 문서·테스트)와
경쟁 라이브러리 비교 분석(PaperTrail, audited, django-auditlog, django-simple-history,
Hibernate Envers, pgAudit, @explita/prisma-audit-log)을 기반으로 0.2.0 범위를 정의한다.
모든 제안은 타당성(실제 코드 재검증)과 사용자 가치(멀티테넌트 SaaS + SOC2 페르소나)
두 관점의 교차 검증을 통과했다.

**0.2.0의 주제: "관측 가능성과 정직한 실패(fail-loud)".**
0.1.0의 결함 패턴은 일관되게 침묵 실패(fail-silent/fail-open)다 — 아무것도 추적하지
않는 기본값, 자동 경로에서 무시되는 `tenantRequired`, 침묵 no-op인 append-only RULE,
`console.warn`뿐인 에러 처리. 컴플라이언스 도구는 반대 성향이어야 한다.

## Must-have

### 1. 보존(retention) 정책 + 파티셔닝 스키마 + prune API

**문제**: append-only RULE이 삭제를 능동적으로 차단해 테이블이 무한 증가한다.
자체 벤치마크조차 정리를 위해 RULE을 drop하는 우회를 쓴다
(`benchmarks/audit-overhead.ts:74-82`). 설계 문서가 retention/archival을 v0.2.0으로
명시적으로 미뤘다(`docs/2026-04-04-audit-log-design.md:258-261`). SOC2는 보존 정책
정의 자체를 요구하므로 "아무것도 못 지운다"는 답은 감사에서 통하지 않는다. 모든
성숙한 경쟁 라이브러리가 보존 기능을 제공한다(PaperTrail `version_limit`,
audited `max_audits`, django-auditlog `auditlogflush`).

**범위**:
- `getAuditTableSQL({ partitioned: true })`: `PARTITION BY RANGE (created_at)`
  월별 파티션 변형. PK를 `(id, created_at)`으로 변경(파티션 키 포함 필수).
  `created_at`에 BRIN 인덱스.
- `AuditService.prune({ olderThan })`: 파티션 `DROP/DETACH` 기반. DML RULE의 영향을
  받지 않는 DDL이므로 append-only와 양립. 테이블 소유자/파티션 drop 권한이 필요함을
  명시 문서화.
- 파티션 수명 관리: `ensurePartitions()` 헬퍼 또는 pg_partman 레시피 문서.
- 기존 flat 테이블 설치용: 권한 있는 연결에서의 rule-drop/recreate 유지보수 경로 문서
  + cron 레시피. **스케줄러는 라이브러리에 포함하지 않는다.**
- 설계 문서가 v0.2.0 항목으로 명시한 JSONB GIN 인덱스 옵션을 같은 스키마 헬퍼
  작업에 포함(`docs/2026-04-04-audit-log-design.md:249`).

**참고**: PostgreSQL 소스(`rewriteDefine.c`) 확인 결과 `CREATE RULE`은 파티션 부모
테이블에도 동작한다. 다만 신규 파티션 레이아웃에는 #11의 트리거 기반 강제가 더
방어적이므로, 일정이 허용되면 트리거 모드를 함께 출시한다.

**일정 압박 시 축소안**: 파티셔닝을 stretch goal로 돌리고, rule-drop/recreate 경로의
`prune({ olderThan })` + cron 문서만 우선 출시(소~중 노력).

### 2. 추적 기본값을 전체 모델로 변경

**문제**: `trackedModels`/`ignoredModels` 둘 다 없으면 `shouldTrackModel`이 false를
반환해 `createAuditExtension({})`이 **아무것도 추적하지 않는다**
(`src/prisma/diff.ts:41-47`). 경고도 없다. 사고/감사 시점에야 발견되는, 컴플라이언스
라이브러리 최악의 실패 모드. 설치 기반이 작은 0.x 시점이 깨기 가장 싼 시점이다.

**범위**:
- 두 옵션 모두 부재 시 전체 모델 추적. `ignoredModels`가 denylist 탈출구.
- 확장 팩토리 호출 시점에 활성 모드 1회 로그 출력(확장은 Nest DI 밖에서 생성되므로
  Nest Logger가 아닌 console/주입 로거 사용).
- 추가 경고: (a) `trackedModels`와 `ignoredModels` 동시 지정 시(현재 allowlist가
  침묵 우선), (b) `trackedModels`가 0개 모델로 해석되거나 알 수 없는 모델명 포함 시
  (오타가 같은 침묵 no-op을 만든다).
- **Breaking**: 기존 빈 설정 설치가 no-op → 전체 추적으로 바뀐다. CHANGELOG 최상단에
  마이그레이션 노트("좁은 추적을 유지하려면 `trackedModels: [...]` 명시") 필수.
- 설계 문서의 구식 설정 예시 갱신.

### 3. 신뢰성 강화

**문제** (셋 모두 코드 재검증 완료):
1. update/delete/upsert의 `findFirst`, deleteMany의 `findMany` pre-read가 try 블록
   **밖**에서 실행된다(`src/prisma/audit-extension.ts:183-185, 237-239, 280-282,
   395-397`). 감사용 조회 실패가 비즈니스 뮤테이션을 중단시킨다 — "감사가 비즈니스를
   깨지 않는다"는 자체 설계 약속 위반. **사실상 버그 수정이므로 0.1.x 패치로 선행
   출시 고려.**
2. 에러 처리가 `tryAuditLog`의 bare `console.warn`(111-116행) + 7개 핸들러의 동일한
   catch 블록뿐. 프로덕션에서 감사 유실이 관측 불가능 — 그 자체가 SOC2 감사 지적
   사항이다.
3. `result`가 'success'로 하드코딩(89행)되어 자동 추적에서 'failure'가 도달 불가.

**범위**:
- pre-read를 try/catch 안으로 이동. 실패 시 감사만 포기하고 뮤테이션은 진행.
- `AuditExtensionOptions.onAuditError?: (error, context) => void` 콜백 + 로거 인스턴스
  옵션(확장은 DI 밖이므로 주입이 아닌 옵션 전달). #4가 이 훅에 의존하므로 선행.
- `logFailures` 옵트인: 비즈니스 쿼리 throw 시 `result='failure'` 항목을 best-effort
  기록. 원본 에러를 반드시 재throw하고, P2025 같은 예상 가능 에러는 제외. ORM 계층
  실패 행은 노이즈가 많으므로 **엄격히 옵트인 유지** — 범위가 커지면 0.3.0으로 분리.

### 4. 테넌트 격리 정합성

**문제**: `tenantRequired` 플래그가 수동 API(`AuditService.log/query`,
`src/services/audit.service.ts:25-29, 55-60`)에서만 검사되고, 자동 경로의
`buildAuditInsertParams`(`src/prisma/audit-extension.ts:48-62`)는 검사 없이
tenant_id NULL 행을 기록한다 — 0.1.0 검증 보고서가 release-blocking으로 지목한
fail-open의 잔존. 또 `query()`는 컨텍스트 부재 시 무스코프 전체 결과를 반환한다
(`src/services/audit.service.ts:63-65`) — 관리자 엔드포인트에 연결되는 순간 교차
테넌트 노출.

**범위**:
- 자동 경로에서 `tenantRequired` 적용: true + 컨텍스트 부재 시 `onAuditError`로 보고
  (비즈니스 쓰기는 중단하지 않음).
- `tenantResolver?: () => string | null` 옵션: `@nestarc/tenancy`의 정확한 API 형태
  (`new TenancyContext().getTenantId()`, `src/utils/tenant.ts:19-20`) 강결합 해소.
  **릴리스 노트의 선두 기능으로 부각** — 임의의 CLS 기반 테넌시와 연동 가능해져
  실질 시장이 열린다.
- `query()`에 명시적 `tenantId` 필터 + 의도적 교차 테넌트 모드는 `allTenants: true`
  같은 명시 플래그로만 도달 가능하게.
- 설정 전달 문제를 선결: `tenantRequired`/`tenantResolver`가
  `AuditExtensionOptions`에도 필요(확장은 모듈 옵션을 볼 수 없음). 모듈/확장 간
  중복 옵션 vs 공유 설정 객체를 의도적으로 결정하고 문서화. #11의 `tableName`도
  같은 문제를 공유하므로 일관된 해법 적용.

### 5. 트랜잭션 정합성 최소 대응

**문제**: 감사 INSERT가 확장 정의 시점에 캡처된 base client로 실행되어 호출자의
`$transaction`에 참여하지 않는다(`src/prisma/audit-extension.ts:65-92`). 롤백 시
**일어나지 않은 변경을 기록한 감사 행이 영구 보존**된다 — 불변 컴플라이언스 로그의
거짓 증거. pre/post read도 커밋된 상태를 읽어 트랜잭션 내 diff가 틀리거나 빈다.
검증 보고서 Finding 1이 release-blocking으로 지목한, 가장 심각한 정확성 결함.

**범위 (0.2.0 최소선)**:
- Prisma extension에서 interactive transaction 클라이언트 접근이 가능한지 조사;
  가능한 범위에서 pre/post read를 트랜잭션 경유로 라우팅.
- 풀 해결(tx-client 플러밍 또는 transactional-outbox 모드)이 막히면: 고아 행 동작의
  정직한 문서화 + 롤백 시나리오 회귀 테스트 + README의 "best-effort" 설명 구체화.
- 설계 문서의 "원자성 보장"(248행) 서술이 실제 best-effort 모델과 모순 — 수정 필수.

### 6. `select` 프로젝션 시 targetId 유실 수정

**문제**: create/upsert에 `select` 프로젝션을 쓰면 결과에 PK가 없어
`result[pkField]`가 undefined → targetId NULL 행 생성
(`src/prisma/audit-extension.ts:140-152, 288-298`; 검증 보고서 Finding 5).
정상적인 핵심 경로에서 깨지는 동작.

**범위**: 쿼리 실행 전 `args.select`에 PK 필드를 주입(작은 수정). 스냅샷 보존을 위해
필요 시 전체 필드 재조회는 기존 update 경로 패턴 재사용.

## Should-have

### 7. 쿼리 API v2

`AuditService.query()`(`src/services/audit.service.ts:53-117`)를 하위 호환 유지하며 확장:

- **커서(keyset) 페이지네이션**: `(created_at, id)` 기준. 무한 증가 테이블에서 offset은
  자해적 스케일링 문제. 기존 `(tenant_id, created_at DESC)` 인덱스와 호환.
  #1 파티션 레이아웃의 정렬을 전제로 설계할 것 — #1 이후 착수 권장.
- **누락 필터**: `actorType`, `source`, `result` (저장되지만 현재 필터 불가),
  명시적 `tenantId`(#4와 한 PR로).
- **`includeTotal` 옵트아웃**: 현재 매 호출마다 무조건 `COUNT(*)`(108-110행)로 비용 2배.
- **`getById(id)`** 단건 조회.
- **와일드카드 이스케이프 버그 수정**: `action.replace(/\*/g, '%')`(71행)가 리터럴
  `%`/`_`를 이스케이프하지 않아 의도치 않은 와일드카드가 된다. 로드맵과 무관한
  정확성 버그.
- 정렬 방향 제어는 범위 압박 시 제외(감사 피드는 사실상 항상 최신순).

### 8. HTTP 밖 액터 컨텍스트

**문제**: `ActorExtractor`가 동기 전용(`src/interfaces/actor.interface.ts:7`)이라
비동기 토큰/세션 조회가 불가. 미들웨어가 무조건 `forRoutes('*')`
(`src/audit-log.module.ts:20`), 인터셉터가 무조건 전역 등록(31행) — 제외 수단 없음.
백그라운드 작업(BullMQ, cron, 이벤트 컨슈머)의 모든 쓰기가 침묵으로
`actorId: null / actorType: 'system'`이 된다.

**범위**:
- `ActorExtractor`를 `(req) => AuditActor | Promise<AuditActor>`로 확장,
  미들웨어 `use()`를 async로.
- 모듈 옵션: 미들웨어 라우트 제외, 전역 인터셉터 등록 해제.
  Nest 11/Express 5의 bare `'*'` 와일드카드 deprecation도 함께 현대화.
- `AuditContext.runAs(actor, fn)` 슈가 + **쿡북 문서**(BullMQ/cron/마이크로서비스
  레시피). 핵심 능력은 이미 공개된 `AuditContext.run`에 있으므로 실질 산출물은 문서.
- 컨텍스트 스토어 없이 감사 대상 쓰기가 실행될 때 1회 경고 — #2와 같은
  fail-loud 철학.

### 9. 컨텍스트 메타데이터 enricher + Correlation ID + `@AuditReason`

범용 프리미티브 위에 두 기능을 구현(같은 노력, 더 넓은 능력):

- **`AuditContext.setMetadata()` / 옵션 콜백**: 자동 항목에 커스텀 메타데이터를
  병합하는 일반 메커니즘. 병합은 `buildAuditInsertParams` 내부 한 곳에서 구현
  (7개 핸들러 개별 수정 회피).
- **Correlation ID**: 설정 가능한 헤더(기본 `x-request-id`, 커스텀 getter 옵션)를
  모든 항목 metadata로 — django-auditlog `AUDITLOG_CID_HEADER` 등가물.
- **`@AuditReason('...')` + `AuditContext.setReason()`**: audited gem `audit_comment`
  등가물. metadata에 저장해 스키마 마이그레이션 회피. `@AuditAction`과 동일한
  요청-단위 적용 범위(요청 내 모든 쓰기에 한 사유) 명시 문서화.
- Prisma 생태계 경쟁자 중 어느 것도 둘 다 없음 — 저비용 차별화.

## Deferred to 0.3.0 (decision required if pulled in)

### 10. 배치 연산 충실도

createMany/updateMany가 `changes: {}`, `targetId: null`, count-only metadata 한 행만
기록(`src/prisma/audit-extension.ts:336-386`) — "벌크 작업이 어떤 레코드를 어떻게
바꿨나"라는 감사 질문에 답 불가. 범위: createMany는 `args.data`에서 레코드별 항목
도출, updateMany는 deleteMany의 pre-read 패턴 적용, deleteMany의 N+1 INSERT 루프를
multi-row INSERT로 교체, `createManyAndReturn`/`updateManyAndReturn`(Prisma 5.14+)
후킹. 주의: `maxBatchRecords` 캡(초과 시 현행 count-only + 경고) 필수, createMany는
DB 생성 PK면 targetId 불가 + `skipDuplicates` 과대 보고 캐비엇, updateMany after-상태
전략(재조회 vs args.data 적용 — `{increment}` 등 원자 연산에서 후자는 오답) 결정 필요.
Breaking: count-only 1행 → N행 형태 변경.

### 11. 테이블명 설정 + 트리거 기반 strict append-only

`'audit_logs'` 리터럴이 4개 SQL 문에 하드코딩(`src/prisma/audit-extension.ts:75`,
`src/services/audit.service.ts:35, 104, 109`). `tableName` 옵션 추가 — 단, 테이블
식별자는 바인드 파라미터 불가이므로 엄격한 식별자 화이트리스트 정규식 검증 +
`Prisma.raw` 보간. strict 모드: 현행 침묵 `DO INSTEAD NOTHING` RULE
(`src/sql/audit-log-schema.sql:21-29`) 대신 `RAISE EXCEPTION` 트리거 +
REVOKE/TRUNCATE 방어 가이드. 신규 생성 DDL은 트리거를 기본으로(RULE은 레거시 호환).
**#1 파티셔닝과 같은 릴리스로 묶어 마이그레이션 1회로** — 이 경우 0.2.0 승격.
