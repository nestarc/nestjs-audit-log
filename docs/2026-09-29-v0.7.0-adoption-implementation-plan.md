# @nestarc/audit-log v0.7.0 구현 계획

- 결정일: 2026-09-29
- 상태: **ALOG-N01 구현 완료 / N02–N05 미착수 / 0.7.0 미배포**
- 기준선: 현재 체크아웃 `0.6.0`, Git `e3fb2d9`
- 목표 버전: `0.7.0`
- 릴리스 주제: **기존 앱에 점진적으로 도입하고, 첫 기록의 정확성을 확인할 수 있게 한다.**
- 문서 목적: 다음 버전의 구현 범위, 공개 계약, 제외 사항, 작업 순서와 완료 기준을 확정한다.

이 문서는 0.7.0 구현 명세와 진행 기록이다. N01은 현재 체크아웃에 구현했으며,
N02–N05의 신규 API와 변경 동작은 아직 제공되지 않는다. N01의 미배포 계약은
[트랜잭션 문서](transactions.md)와 [CHANGELOG](../CHANGELOG.md)의 Unreleased를 따른다.
그 밖의 현재 지원 계약은 [README](../README.md), [API reference](api-reference.md)를 따른다.
패키지 버전과 배포 상태는 변경하지 않는다.
`0.6.0`은 로컬 기준 버전이며 npm 최신 배포 버전이라고 가정하지 않는다.

## 1. 제품 결정

첫 대상은 **NestJS + Prisma + PostgreSQL을 이미 사용하며, 중요한 모델의 변경자와
변경 전후 값을 자기 DB에 보관하고 고객 문의·운영 사고에서 조회하려는 SaaS 백엔드 팀**이다.

이번 버전은 다음 두 도입 경로를 완성한다.

1. **업무 이벤트부터 시작:** 기존 `$transaction()` 안에서 `AuditService.log(input, tx)`로
   중요한 이벤트 하나를 기록한다. 자동 추적 extension이나 업무 트랜잭션 구조 변경은 필수가 아니다.
2. **모델 하나의 자동 변경 이력 추가:** `trackedModels`로 범위를 좁히고 해당 쓰기 경로에
   `withAuditTransaction()`을 적용한다. 인증된 actor, tenant, 민감정보 마스킹과 rollback을 검증한다.

성공의 단위는 "설치 완료"가 아니라 **실제 인증·테넌트 환경에서 올바른 첫 기록을 조회한 상태**다.
자동 추적을 위한 기존 트랜잭션 helper와 nested/bulk 제한은 유지한다. 이를 감추거나
`best-effort`를 동등한 정합성의 대안으로 안내하지 않는다.

## 3. 구현 명세

### ALOG-N01 — 지원하지 않는 자동 쓰기를 실행 전에 차단

**결정:** 추적 대상 모델의 `createManyAndReturn`·`updateManyAndReturn`을 명시적으로 처리한다.
이번 버전에 두 작업의 레코드별 감사 기능을 추가하지 않는다.

| 조건 | 결정한 동작 |
|---|---|
| 추적 대상 + `atomic-required` | helper 안팎 모두 business query 실행 전에 거절 |
| helper 안에서 위 오류를 catch | atomic 실패 상태를 남겨 callback 종료 시 트랜잭션 전체 거절 |
| 추적 대상 + `best-effort` | 기존 business query와 반환값을 유지하고, 자동 기록 미지원 경고를 새로 제공 |
| 제외 모델 또는 `@NoAudit()` | 기존 명시적 추적 제외 동작 유지 |
| 해당 API가 없는 Prisma 버전 | extension 생성·기존 작업에 영향을 주지 않음 |

- best-effort 경고는 extension 인스턴스 안에서 모델·operation 조합별 한 번 발생시킨다.
  주입 logger를 사용하고 logger 오류는 business query에 영향을 주지 않는다.
- 경고/오류는 모델·operation·권장 대안인 단일 레코드 쓰기를 알려준다.
  요청 데이터나 민감한 필드 값은 포함하지 않는다.
- atomic 거절은 기존 감사 실패 상태 관리와 연결한다. 단순히 `throw`만 추가하고
  callback에서 catch한 뒤 커밋할 수 있게 두지 않는다.
- 알려진 두 API에 대한 제한된 가드다. base client·raw SQL·DB cascade·향후 Prisma의
  모든 신규 API까지 탐지하거나 DB 전체의 변경을 수집한다고 주장하지 않는다.
- `createMany`·`updateMany`, nested writes 및 soft-delete lifecycle의 기존 계약은 유지한다.

구현 위치: `operation-handlers/index.ts`, `operation-handlers/types.ts`, `mutation-policy.ts`,
`audit-extension.ts`의 실패 상태 연결. 중복 정책은 공통 함수로 처리한다.

완료 기준:

- 두 operation에서 거절 전 business query가 한 번도 호출되지 않는다.
- helper 안에서 앞선 정상 쓰기 후 미지원 작업 오류를 catch해도 앞선 쓰기·감사 행이 모두 rollback된다.
- excluded/NoAudit 경로와 best-effort의 반환값·원본 business 오류가 보존된다.
- PostgreSQL E2E로 실제 지원되는 Prisma 버전의 DB 불변·rollback을 검증한다.
  두 API가 없는 peer lane에서는 생성·타입·기존 operation 호환성을 검증한다.
- [트랜잭션 계약](transactions.md)의 bulk 표와 `0.6 → 0.7` 마이그레이션 안내를 갱신한다.

### ALOG-N02 — 식별 가능한 actor를 요구하는 정책

**결정:** `AuditSharedOptions`에 `actorRequired?: boolean`을 추가한다. 기본값은 `false`다.
`true`이면 `user`, `system`, `api_key` 모두 **공백을 제외한 길이가 1 이상인 문자열 ID**가 필요하다.
검증을 통과한 ID 자체를 trim하거나 바꾸지는 않는다. actor 객체만 존재하는 것은 충분하지 않다.

| 경로 | `actorRequired: true` + 유효 actor 없음 |
|---|---|
| 자동 atomic 추적 | business query 전 거절, 활성 helper 실패 표시 및 전체 rollback |
| 자동 best-effort 추적 | business 동작 보존, actor 정책 오류 보고, 해당 자동 감사 행 생략 |
| 수동 `AuditService.log()` | 감사 INSERT 전에 오류 반환; tx 전달 여부와 무관 |
| 조회·CSV·scan | 쓰기 actor 정책을 적용하지 않음; 기존 tenant/인가 책임 유지 |
| 제외 모델·`@NoAudit()`의 자동 쓰기 | 기존 추적 제외 동작 유지 |
| `@NoAudit()`에서 명시적으로 호출한 수동 log | actor 정책 적용 |

- 자동 쓰기는 추적 제외 판단 후, business query 전 actor를 검증한다. 해당 operation의 기록에는
  검증한 actor 값의 복사본을 사용하여 검증한 값과 저장 값이 달라지지 않게 한다.
- 지원되는 단일 쓰기·bulk·lifecycle 경로에 같은 정책을 적용한다.
- `onAuditError`에는 기존 `phase: 'context'`와 가능한 모델·operation 정보를 전달한다.
  오류 보고 훅이 실패해도 원래 정책을 바꾸거나 business 오류를 덮지 않는다.
- worker는 `AuditContext.runAs({ id: 'invoice-worker', type: 'system' }, callback)`처럼
  명시적인 주체를 제공한다. `runAs()`가 tenant까지 생성하는 것으로 안내하지 않는다.
- HTTP actor 추출 단계의 기본값은 `middleware`로 유지한다. Guard 인증 예제는
  `actorExtractionStage: 'interceptor'`를 명시한다. actor 정책은 인증/인가 기능이 아니다.
- extractor가 실패하더라도 읽기 요청 전체를 거절하는 정책을 새로 추가하지 않는다.
  추적 대상 쓰기에 도달했을 때 위 정책을 적용한다.

**수동 트랜잭션의 경계:** `log(input, tx)`의 JavaScript 오류를 호출자가 catch하면,
일반 Prisma transaction은 다른 business 변경을 커밋할 수 있다. 수동 log에 자동 helper의
실패 표시가 연결된다고 약속하지 않는다. 원자적인 수동 이벤트 예제는 오류가 callback 밖으로
전파되게 하고, 이 제한을 API 문서와 테스트에 명시한다. 이번 버전은 임의의 외부 transaction을
추적하거나 강제로 실패시키는 별도 transaction registry를 구현하지 않는다.

구현 위치: shared options, actor 검증 공통 함수, 자동 operation 처리, `audit-insert.ts`,
`AuditService.log()`. 공통 actor 판정 규칙을 한 곳에서 관리한다.

완료 기준:

- default false에서 현재 null/system 기록 호환성을 유지한다.
- HTTP Guard actor, worker system actor, api_key actor가 각각 유효 ID로 통과한다.
- null·빈 문자열·공백 ID는 거절되거나 위 best-effort 정책대로 보고·생략된다.
- atomic callback이 정책 오류를 catch해도 이전 쓰기까지 rollback된다.
- 수동 log의 오류 전파/호출자 catch 차이를 검증하고 보장 범위를 문서화한다.
- 동시 요청 간 actor가 섞이지 않고, automatic/manual masking과 tenant 동작이 유지된다.

### ALOG-N03 — 공통 설정을 한 번 정의하는 API

**결정:** 공개 함수 `defineAuditConfig()`를 추가한다. 이 함수는 동기적인 순수 옵션 생성기다.
Prisma client 생성, DB 접속, schema 적용, Nest 등록, 인증 추론을 수행하지 않는다.
기존 `forRoot`, `forRootAsync`, `createAuditExtension`, `createAuditedClient`는 계속 지원한다.

입력과 출력 계약:

| 입력 | 내용 |
|---|---|
| `shared` | `tableName`, `prismaModule`, tenant 정책, `actorRequired`, masking, logger, onAuditError |
| `module` | actorExtractor, actorExtractionStage, route/interceptor/correlation 설정; prisma와 shared 필드 제외 |
| `extension` | consistency, tracked/ignoredModels, PK/mapping, batch 및 자동 추적 옵션; shared 필드 제외; 수동 전용이면 생략 |
| `schema` | partitioned, enforcement, ginIndex; tableName 제외; 생략 가능 |

| 출력 | 사용 방법 |
|---|---|
| `moduleOptions` | `AuditLogModule.forRoot({ ...config.moduleOptions, prisma: base })` |
| `extensionOptions` | `createAuditedClient(base, config.extensionOptions)`; extension 입력을 생략하면 undefined |
| `schemaOptions` | `applyAuditTableSchema(setupClient, config.schemaOptions)` |
| `partitionOptions` | `ensurePartitions(maintenanceClient, { ...config.partitionOptions, ahead: 1 })` |

공통 필드 목록은 `AuditSharedOptions`에만 한정하지 않는다. 현재 module과 extension에 중복된
`prismaModule`, `sensitiveFields`, `sensitiveFieldsByModel`도 포함한다. DDL과 partition 옵션에는
이 중 `tableName`만 전달하고 actor/extractor/tenant 정보를 섞지 않는다.

```typescript
// 0.7.0 목표 API 예시. 현재 체크아웃에서 실행 가능한 코드는 아니다.
const config = defineAuditConfig({
  shared: {
    prismaModule: { Prisma },
    tableName: 'audit_logs',
    tenantRequired: true,
    tenantResolver,
    actorRequired: true,
    sensitiveFields: ['password', 'ssn'],
  },
  module: {
    actorExtractionStage: 'interceptor',
    actorExtractor,
  },
  extension: {
    consistency: 'atomic-required',
    trackedModels: ['User'],
    databaseMapping: { User: { tableName: 'users' } },
  },
  schema: { partitioned: false },
});

const audited = createAuditedClient(base, config.extensionOptions);
// Nest useFactory에서는 { ...config.moduleOptions, prisma: base }를 반환한다.
// 별도 migration/setup에서 config.schemaOptions를 사용한다.
```

- `extension`이 있으면 `consistency`를 반드시 명시한다. factory가 모드를 추정하지 않는다.
- input overload/조건부 타입으로 extension을 제공한 호출의 `extensionOptions`는
  `undefined`와의 union 없이 사용 가능해야 한다. 수동 전용 호출은 extension 없이 유효하다.
- shared 필드를 개별 section에서 재정의할 수 없게 타입에서 제외한다. `any`/JavaScript 입력도
  중복 필드를 조용히 덮어쓰지 않고, 잘못된 설정 위치를 포함한 오류로 거절한다.
- 생략한 옵션의 기존 기본 동작을 보존한다. 유효성 검사는 가능한 한 기존 검증 함수를 재사용한다.
- 배열·일반 설정 객체는 입력 및 각 출력 사이에 mutable 참조를 공유하지 않게 복사한다.
  함수·logger·Prisma namespace를 JSON 직렬화하거나 재귀 freeze하지 않는다.
- 이는 생성 시점의 일관성 제공이다. 출력 후 사용자가 옵션을 수정·덮어쓴 경우까지
  감시하거나 기존의 독립 등록 API를 런타임 병합하지 않는다.

완료 기준:

- custom tableName으로 DDL 생성, 수동 INSERT, 자동 INSERT, 조회가 같은 테이블을 사용한다.
- tenant/actor/masking 설정이 automatic/manual 양쪽에 적용된다.
- factory 생성 후 입력 배열을 바꿔도 생성된 설정이 변하지 않는다.
- 수동 전용·자동 추적·forRootAsync 예제를 public export로 컴파일한다.
- 생성된 audited client의 모델·transaction callback 타입 추론을 유지한다.
- 설정만 만드는 호출에는 DB I/O나 Prisma client 생성 부수 효과가 없다.

### ALOG-N04 — 소비자 기준 첫 성공과 점진 도입 안내

**결정:** 기본 README의 시작 경로를 배포 패키지 소비자에게 맞춘다. checkout build/pack은
기여자·후보 버전 검증 경로로 옮기며, 기존 runnable example과 검증 스크립트를 재사용한다.

구현 산출물:

1. **버전이 고정된 설치 경로.** 검증된 npm 배포 버전, 해당 버전 API, 예제를 함께 안내한다.
   배포 전에는 존재하지 않는 `@0.7.0` 설치를 현재 사용 가능한 절차로 제시하지 않는다.
   개발 문서는 candidate임을 표시하고 tarball 경로를 별도 안내한다.
2. **수동 이벤트 시작 가이드.** 기존 transaction에서 업무 변경과 `log(input, tx)`를 함께 실행하고
   실패를 전파하는 예제를 제공한다. 별도 automatic extension 없이 설정할 수 있어야 한다.
3. **모델 하나의 자동 추적 가이드.** 기존 `$transaction`·nested·bulk 코드의 변경 전후 예제를
   제공한다. 감사 대상 모델의 쓰기 경로를 확인하는 짧은 체크리스트를 포함한다.
4. **업무 결과까지 이어지는 예제.** 사용자 권한 변경 → actor/tenant/before-after 기록 →
   해당 tenant의 권한 있는 운영자 조회로 연결한다. 기존 생성 예제와 함께 검증 가능한 흐름을 만든다.
5. **인증·worker 예제.** Guard 이후 actor 추출과 worker의 actor/tenant 문맥을 각각 설명한다.
   고정된 데모 주체와 실제 애플리케이션의 인증·인가 책임을 구분한다.

- 새 `docs/adoption-guide.md`에 점진 도입을 모으고 README·agent-guide·llms.txt에서 연결한다.
- 새 소비자 문서/예제는 `package.json` files와 packed-consumer 검증 대상에 포함한다.
- 사이트는 별도 저장소 작업이다. 해당 변경과 배포 확인을 릴리스 체크리스트로 추적하고,
  이 저장소 파일을 고친 것만으로 사이트 동기화를 완료 처리하지 않는다.
- `test/docs.spec.ts`의 "current checkout" 문구 강제는 배포/개발 경로를 구분하는
  버전 계약 검증으로 갱신한다. 링크·포장 누락 검사 자체는 유지한다.
- 문서상의 한계를 지워 설치가 쉬워 보이게 만들지 않는다. base client/raw SQL/DB cascade,
  nested/bulk 및 stream의 late-commit 경계를 한 곳에서 찾을 수 있게 유지한다.

완료 기준: 수동/자동 두 경로 모두 실제 packed package로 실행되고, 첫 기록의 actor·tenant·
masking·원자성을 확인하는 명령과 기대 결과가 문서에 연결된다.

### ALOG-N05 — 소비자가 결과를 확인하는 검증 경로

**결정:** 기존 `test:docs:consumer`와 quick-start smoke를 확장한다. 별도의 설치 CLI,
전체 저장소 정적 분석기, 범용 health-check 서비스는 만들지 않는다.

필수 검증 시나리오:

| 시나리오 | 확인할 결과 |
|---|---|
| 인증 Guard 이후 권한 변경 | actor ID, tenant, 대상 ID, before/after가 정확함 |
| worker 실행 | 명시한 system actor와 별도로 설정한 tenant가 기록됨 |
| 같은 설정의 automatic/manual | 비밀 값 마스킹과 tenant 정책이 양쪽에서 일치함 |
| business 예외와 자동 감사 실패 | transaction 내 business 변경과 audit 행이 함께 rollback됨 |
| N01/N02 정책 오류를 catch | 자동 helper가 커밋을 거절함 |
| 기존 transaction + 수동 이벤트 | 오류를 전파하면 함께 rollback됨; catch 시의 경계도 검증됨 |
| 대상 tenant 조회 | 다른 tenant의 기록이 섞이지 않음; 인가 자체는 호스트에서 수행 |
| custom tableName | DDL·수동/자동 저장·조회가 모두 설정된 테이블 사용 |
| tracked/excluded/NoAudit 구분 | 의도한 자동 추적 제외와 수동 기록 계약 유지 |

- 저장소 source 상대 import 없이 실제 tarball과 public API를 사용한다.
- 기존 격리된 로컬 테스트 DB/schema와 teardown을 사용한다. 사용자의 production DB에
  검증용 데이터를 쓰거나 trigger를 해제하는 진단을 제공하지 않는다.
- 소비자가 자기 테스트 환경에 옮길 수 있도록 assertion 예제를 문서화한다.
  예제 fixture의 성공을 사용자 애플리케이션 전체의 감사 완전성으로 표현하지 않는다.
- candidate와 registry 설치를 구분한다. 배포 후에는 실제 registry artifact로 설치·컴파일·
  smoke를 확인하고 설치 버전/출처를 증거로 남긴다.

완료 기준: CI에서 확장된 packed-consumer 검증을 통과하고, 필수 시나리오와 문서 예제의
대응 관계를 기록한다. 테스트 개수나 mock 호출 횟수만으로 완료 처리하지 않는다.

## 4. 이번 버전에서 제외하는 내용

| 제외 항목 | 이유 | 다시 검토할 조건 |
|---|---|---|
| TypeORM/Drizzle, 다른 DB 지원 | 초기 대상의 도입 비용을 직접 낮추지 않음 | 해당 stack의 실제 도입 요청과 유지보수 여력이 확인됨 |
| nested·bulk 자동 감사 전면 지원 | transaction/정확성 범위가 크게 확대됨 | 후보 앱의 도입 실패가 특정 연산에 반복 집중됨 |
| 기존 `$transaction`의 투명한 자동 인식 | 새 정합성·extension 조합 계약이 필요함 | 점진 도입으로도 변경량이 허용 범위를 넘는 증거가 있음 |
| 고객용 관리 UI/RBAC 제품 | 사용자별 완성 기능 요구가 아직 검증되지 않음 | 조회 화면 부족 때문에 도입이 중단된 사례가 반복됨 |
| CDC·commit 순서 보장 외부 수집 | 별도 아키텍처와 운영 범위 | 모든 commit의 외부 전달이 핵심 요구인 고객군을 선택함 |
| 내장 scheduler·분산 lease·DLQ 운영 도구 | 운영 플랫폼 책임 확대 | 기존 호스트 조합으로 해결되지 않는 반복 요구 확인 |
| 신규 SIEM/provider sink | 이미 export·여러 sink가 있음 | 특정 목적지 부재가 실제 도입 차단 원인임 |
| 저장소 정적 분석 CLI/codemod | alias·DI·동적 코드 분석 정확성과 관리 비용이 큼 | 수동 적용 사례에서 분석 패턴과 절감 효과를 확보함 |
| 대규모 벤치마크 프로젝트 | 아직 대표 고객 workload가 없음 | 후보 팀의 성능 예산과 대표 데이터/부하를 확보함 |
| actor 정책의 모델별 callback/복잡한 예외 규칙 | 첫 정책의 학습·검증 부담을 제한 | 단일 boolean으로 표현할 수 없는 실제 요구 확인 |

운영·성능 문서의 기존 정보는 유지한다. 이번 릴리스에서 성능 향상, 운영 부담 제거,
DB 전체 추적, 변조 불가능성, 모든 commit의 외부 전송을 새로운 보장으로 내세우지 않는다.

## 5. 호환성과 마이그레이션 결정

- **목표는 0.7.0이다.** 현재 atomic 모드에서 통과하던 두 `*ManyAndReturn` 작업을 거절하므로
  동작 변경을 명시적으로 릴리스한다. 0.6.x patch에 조용히 포함하지 않는다.
- 해당 작업 사용자는 supported 단일 레코드 operation으로 변경하거나, 기존 base transaction의
  수동 업무 이벤트로 전환한다. 수동 이벤트가 자동 before/after 증거를 대신 만들어 준다고 설명하지 않는다.
- `best-effort`는 기존 business 동작을 유지하되 미지원 경고가 추가된다.
  정합성 제약을 피하기 위한 기본 마이그레이션 경로로 권장하지 않는다.
- `actorRequired`는 기본 false이고, `defineAuditConfig()`는 추가 API다. 기존 등록 방식과
  actor 추출 기본 시점을 유지한다. actorRequired를 켤 때 HTTP/worker/system ID 설정을 안내한다.
- 스키마 변경은 요구하지 않는다. 기존 감사 행을 backfill하거나 actor ID를 추정해 채우지 않는다.
- peer/Node 지원 범위를 이번 목적을 위해 확대·축소하지 않는다. 기존 조합의 CI를 유지한다.
- tenancy/soft-delete의 audit-log peer range가 0.7을 허용하는지 후보 설치에서 확인한다.
  불일치하면 companion release의 명시적 의존 작업으로 기록한다. `--force`나
  `--legacy-peer-deps`로 gate를 통과시키지 않는다.
- 기존 published ecosystem fixture는 검증된 exact tuple을 유지한다. publish 전 candidate
  검증과 publish 후 새 exact tuple 갱신을 구분한다.

## 7. 기술적 완료 기준과 릴리스 절차

구현 작업에서 다음 기존 검증을 유지하고 변경 영역의 검증을 확장한다. 아래 명령은 이 계획 작성
시점에 실행한 결과가 아니며, 향후 릴리스 전 완료해야 할 항목이다.

```bash
npm run lint
npm run typecheck
npm run build
npm run test:cov -- --runInBand
npm run test:e2e:full
```

packed-consumer와 ecosystem 검증에는 별도 PostgreSQL 실행이 필요하다. `test:e2e:full`이
자체 teardown을 수행하므로 DB가 계속 실행 중이라고 가정하지 않는다. [maintaining](maintaining.md)의
격리 DB 절차에 따라 아래 검증을 실행하고 실패 시에도 DB/schema 정리를 보장한다.

```bash
npm run docker:up -- --wait --wait-timeout 60
npm run test:docs:consumer
npm run test:e2e:ecosystem
npm run test:e2e:ecosystem:candidate
npm run docker:down
```

릴리스 완료 조건:

- N01–N05의 동작 기준과 기존 Node/Nest/Prisma peer matrix를 통과한다.
- actor 정책·unsupported operation의 atomic 동작은 PostgreSQL E2E 증거가 있어야 한다.
- 배포 tarball에 실제 실행에 필요한 문서·예제가 포함되고 public export의 타입이 검증된다.
- 현재 버전과 목표 버전의 계약을 섞지 않는 migration guide와 CHANGELOG를 작성한다.
- 기존 release workflow와 strict peer ecosystem gate를 통과한다.
- publish 후 registry artifact 설치 검증, exact tuple 갱신, 공개 사이트의 버전별 안내를 확인한다.
  외부 단계가 미완료면 이를 미완료로 기록하고, 후보 테스트 성공만으로 완료 처리하지 않는다.

배포·외부 사이트 변경은 이 계획의 후속 실행 작업이다. 최초 범위 결정 이후 N01 구현까지
진행했으며, 태그 생성·npm 게시·사이트 배포는 수행하지 않았다.

## 8. 제품 가설 검증

기술적 테스트 통과와 사용자 채택 개선은 별도로 측정한다. 아래 수치는 관찰값이 아닌
**검증 목표**이며, 실제 참가자가 확보되지 않으면 결과를 미측정으로 남긴다.

| 실험 | 방법 | 목표/기록할 값 |
|---|---|---|
| 첫 성공 | DB와 기존 앱 준비를 마친 외부 개발자 5명에게 문서만 제공 | 4명 이상이 30분 안에 actor/tenant/masking이 맞는 첫 기록 조회; 환경 준비 시간은 별도 기록 |
| 점진 도입 비용 | 실제 후보 앱 3개에서 중요 모델 또는 업무 이벤트 하나 적용 | 수정 파일 수, 필요한 write 재작성, 소요 시간, 중단 이유; 무수정 적용률을 가정하지 않음 |
| 검증 도움 | 의도적으로 잘못된 actor/tenant/masking 설정을 테스트 환경에 적용 | 사용자가 배포 전에 문제를 발견하고 올바른 설정으로 복구하는지 확인 |

인터뷰는 최근 변경 이력 조사 사건, 현재 해결 방법, 실제 소요 시간, 해결하지 못한 부분을 묻는다.
기능 선호 답변이나 다운로드 수만으로 채택 장벽이 해소됐다고 판단하지 않는다.
실험 결과가 나쁘면 먼저 실패 단계의 설정·가이드·동작을 개선한다. 후속 기능은 §4의
재검토 조건에 해당하는 증거가 있을 때 별도 버전 범위로 결정한다.

### ALOG-N01 구현 결과

- `operation-handlers/index.ts`, `types.ts`, 신규 `unsupported.ts`: 두 returning operation을
  명시적으로 등록하고, 기존 추적 제외 판단 후 공통 정책을 적용한다.
- `mutation-policy.ts`: atomic 사전 거절과 best-effort 경고를 공통 처리한다. atomic 오류는
  `reportAuditError()`를 통해 기존 `markAtomicFailure`에 연결해 callback이 catch해도
  helper 완료를 거절한다. 경고/오류에는 모델·operation·단일 레코드 대안만 포함한다.
- `audit-extension.ts`: extension 생성 시 경고 Set을 만들고 handler에 전달한다.
  동일 extension을 여러 client에 적용해도 경고를 공유하고, 별도 extension은 독립적으로 경고한다.
  logger가 throw해도 best-effort business query의 반환값/원본 오류를 유지한다.
- `test/audit-extension-queries.spec.ts`, `test/audit-operation-handlers.spec.ts`:
  query 미호출, catch 후 helper 거절, 오류 보고 훅 실패, 경고 중복 억제, 요청 값 비노출,
  allowlist/denylist/빈 목록/NoAudit, 반환값·오류 보존을 검증한다.
  `test/audit-nested-writes.spec.ts`의 공통 의존성 fixture도 갱신했다.
- 신규 `test/e2e/unsupported-returning.e2e-spec.ts`: 실제 PostgreSQL에서 helper 밖 DB 불변,
  helper 안 선행 business/audit 행의 rollback, best-effort·excluded·NoAudit 동작을 검증한다.
  API가 없는 peer는 해당 API 테스트만 skip하고 extension 생성과 기존 atomic create 검증은 실행한다.
- `test/e2e/transactions-atomic.e2e-spec.ts`: 기존 update 검증에서 생성·수정 timestamp가
  같은 밀리초일 수 있는 비결정성을 제거하기 위해 seed의 `updatedAt`을 과거 값으로 고정했다.
- [트랜잭션 계약](transactions.md)의 bulk 표와 `0.6 → 0.7` 마이그레이션 안내,
  [CHANGELOG](../CHANGELOG.md)의 Unreleased를 갱신했다. 단일 레코드 대안과 수동 이벤트의
  증거 범위를 구분하고 기존 bulk/nested/lifecycle 계약을 유지한다.

### ALOG-N01 검증 결과

로컬 Node.js `24.11.1`, NestJS `12.0.1`, Prisma `7.9.1`, Docker PostgreSQL 16 기준:

| 실행 명령 | 결과 |
|---|---|
| `npm run lint` | 통과 |
| `npm run typecheck` | 통과 |
| `npm run build` | 통과 |
| `npm run test:cov -- --runInBand` | 25 suites / 427 tests 통과; lines 93.92%, branches 86.82%; 기존 coverage gate 통과 |
| `npm run test:e2e:full` | 13 suites / 92 tests 통과; N01 신규 11개 포함; PostgreSQL 컨테이너 teardown 완료 |

HTTP 테스트의 최초 실행은 sandbox의 `listen EPERM`으로 실패했으며, 로컬 listen 권한을
허용한 재실행에서 전체 통과했다. E2E fixture 타입 오류는 수정 후 typecheck와 E2E를 재검증했다.

두 API가 없는 Prisma `5.13.0`은 `/private/tmp`의 격리 복사본에 exact 버전으로 설치해 검증했다.
원본 manifest/lockfile은 변경하지 않았다. `PRISMA_TEST_CLIENT=legacy`와 로컬 `audit_test` DB에서:

| 실행 명령 | 결과 |
|---|---|
| `prisma generate --schema=test/e2e/prisma/schema.legacy.prisma` | 5.13.0 client 생성 통과 |
| `prisma db push --schema=test/e2e/prisma/schema.legacy.prisma --skip-generate` | 격리 테스트 DB schema 적용 통과 |
| `npm run typecheck` / `npm run build` | 통과 |
| `npm test -- --runInBand test/audit-extension-queries.spec.ts test/audit-operation-handlers.spec.ts test/public-api.spec.ts` | 3 suites / 125 tests 통과 |
| `npm run test:e2e -- test/e2e/unsupported-returning.e2e-spec.ts test/e2e/transactions-atomic.e2e-spec.ts` | 2 suites / 23 tests 통과; 없는 두 API의 10개 시나리오만 skip; 기존 atomic operation·extension 생성 유지 확인 |

Prisma 5.13 최초 E2E에서 위 timestamp fixture 비결정성을 발견해 수정했고, 재실행은 통과했다.
호환성 실행도 종료 시 PostgreSQL 컨테이너와 네트워크를 정리했다. 신규 E2E는 기존 CI의
peer-matrix에도 포함되며 해당 client가 실제 제공하는 API에 한해 returning operation을 실행한다.

남은 범위: N02–N05, 전체 Node/Nest/Prisma CI matrix 및 packed-consumer/ecosystem release gates,
실제 0.7.0 게시와 사이트 연계는 아직 완료한 것으로 간주하지 않는다.
base client·raw SQL·DB cascade·향후 신규 API의 변경 탐지는 N01 범위 밖이다.
