## 1. 문서 사용법

새 세션은 대화 기록을 전제로 하지 않고 이 문서만으로 시작할 수 있어야 한다.

1. 아래 **세션 시작 절차**를 실행한다.
2. 작업 표에서 의존성이 모두 끝난 첫 `READY` 항목 하나만 선택한다.
3. `rg -n "^### ALOG-MNN"`으로 선택한 작업의 상세 절을 찾아 끝까지 읽는다.
4. 선택한 항목을 `IN_PROGRESS`로 바꾸고 해당 작업의 `Handoff`를 갱신한다.
5. 한 세션에서 관련 있어 보이는 다른 작업까지 섞지 않는다.
6. 완료 조건과 검증 명령을 모두 충족한 뒤에만 `DONE`으로 바꾼다.
7. 세션 종료 전에 이 문서의 작업 표, 개별 `Handoff`, 하단 작업 로그를 갱신한다.

상태 값:

- `BACKLOG`: 순서는 정해졌지만 아직 착수할 수 없다.
- `READY`: 의존성이 충족되어 바로 시작할 수 있다.
- `IN_PROGRESS`: 현재 세션이 이 작업을 수행 중이다.
- `BLOCKED`: 사용자 결정, 외부 저장소 또는 외부 환경이 필요하다.
- `DONE`: 완료 조건과 검증 증거가 모두 기록됐다.
- `DROPPED`: 이유와 결정자를 기록하고 의도적으로 제거했다.

### 2.5 즉시 확인된 correctness 위험

`withAuditLifecycle()`는 `suppressOuterOperation`을 배열에 push한 뒤 callback을 실행한다.
callback이 실제 delete/deleteMany를 호출하기 전에 실패하면 suppression이 소비되지도, `finally`에서
정리되지도 않는다. 호출자가 같은 `withAuditTransaction()` 안에서 오류를 catch하고 다음 동일 모델
delete를 실행하면 오래된 suppression이 정상 audit row를 삼킬 수 있다.

이 위험은 `ALOG-M01`에서 가장 먼저 재현하고 수정한다.

## 5. 작업 단위

### ALOG-M01 — lifecycle suppression을 callback scope에 묶는다

#### Status

- Priority: P0
- State: DONE
- Base ref: `v0.4.0` / `6e1373b`
- Owner: Codex (2026-08-27 session)
- Blocks: `ALOG-M06`, `ALOG-M16`

#### Context

`createAuditExtension()` 내부 `withAuditLifecycle()`는 suppression 항목을 배열에 push한다. 정상
delete/deleteMany가 실행되면 query handler가 이를 소비하지만, callback이 먼저 throw하면 항목이
남는다. 같은 atomic transaction callback이 오류를 catch한 뒤 실행하는 다음 동일 모델 mutation이
잘못 suppress될 수 있다. 감사 누락 가능성이므로 리팩터링보다 먼저 수정한다.

#### Goal

각 suppression을 고유 token 또는 명시적 scope로 관리하고 callback 성공·실패와 관계없이 해당
호출이 만든 미소비 suppression만 `finally`에서 제거한다.

#### Non-goals

- soft-delete sibling 구현 또는 릴리스
- lifecycle action naming 변경
- transaction API 재설계
- operation handler 파일 분해

#### Files

- Primary: `src/prisma/audit-extension.ts`
- Unit tests: `test/audit-extension-queries.spec.ts`
- PostgreSQL E2E: 기존 atomic suite 또는 전용 lifecycle regression suite
- Docs: 사용자 계약이 바뀌지 않으면 README 변경 없음

#### Steps

1. lifecycle callback이 mutation 전에 throw하는 characterization test를 추가한다.
2. 호출자가 오류를 catch한 뒤 같은 모델의 일반 delete/deleteMany를 실행하는 회귀를 추가한다.
3. suppression 항목에 호출별 identity를 부여하고 `try/finally`로 미소비 항목만 정리한다.
4. 정상 lifecycle 경로가 여전히 outer generic audit을 한 번만 suppress하는지 검증한다.
5. 실제 PostgreSQL transaction commit/rollback 경로를 검증한다.

#### Acceptance

- [x] 실패한 lifecycle callback 뒤 다음 일반 delete가 정확히 한 개의 generic audit row를 남긴다.
- [x] 실패한 lifecycle callback 뒤 다음 deleteMany도 잘못 suppress되지 않는다.
- [x] 정상 soft-delete bridge는 lifecycle audit만 한 번 남기고 generic outer audit은 남기지 않는다.
- [x] 다른 모델/operation의 suppression과 간섭하지 않는다.
- [x] 공개 타입과 기존 정상 동작은 변하지 않는다.
