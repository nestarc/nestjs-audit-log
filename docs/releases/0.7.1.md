# audit log 0.7.1 release notes

Version 0.7.1 adds opt-in SQL Server manual audit logging and audit table installation while
preserving PostgreSQL as the default provider. The [Quick Start](../../README.md#quick-start)
documents installation of `@nestarc/audit-log@0.7.1` for PostgreSQL; use the
[SQL Server guide](../sql-server.md) for an existing SQL Server application.
See the [CHANGELOG](../../CHANGELOG.md) for version changes.

## SQL Server manual logging

Configure `provider: 'sqlserver'` and pass the application's generated `Prisma` namespace to use
`AuditService.log(input, tx?)`. Passing the business transaction's client writes the audit row on
that transaction, so successful business and audit writes commit together. An error propagated
out of the transaction callback rolls both back. Manual events retain actor and tenant policy,
context metadata, reason, and redaction behavior.

The SQL Server schema utilities install a flat audit table with Unicode `NVARCHAR(MAX)` text,
JSON checks, UTC timestamps, a clustered `(created_at, id)` index, and UPDATE/DELETE rejection
triggers. The installer executes trigger definitions in separate batches, validates existing
layouts, and restores trigger enforcement when reapplied. Omitting the provider continues to
select PostgreSQL. Existing PostgreSQL automatic tracking and storage APIs retain their behavior.

Use the [SQL Server guide](../sql-server.md) for module registration, transaction examples,
installation privileges, and executable DDL formats.

## Supported environment and current limits

The SQL Server validation uses Linux x64 Ubuntu 24.04, Node 24.11.1, SQL Server 2025 CU10, and
Prisma CLI, client, and MSSQL adapter pinned to 7.10.0. The preflight records the actual server
version and container image digest. This validation does not establish support for every SQL
Server build or Prisma version in the package's PostgreSQL peer matrix.

- SQL Server automatic tracking, `createAuditedClient`, `createAuditExtension`, and factory
  `extension` configuration are unsupported and rejected.
- SQL Server query, lookup, scan, CSV export, retention, partitions, GIN indexes, and rule
  enforcement are unsupported. The PostgreSQL stream store remains PostgreSQL-specific.
- Manual atomicity requires the caller to pass the same business transaction and propagate
  audit failures. Omitting `tx` uses the base client; catching a JavaScript policy error does
  not itself force transaction rollback.
- Schema installation supports compatible flat tables. It does not migrate arbitrary existing
  layouts or convert PostgreSQL tables, and its DDL batches are not wrapped in one transaction.
- Mutation triggers reject UPDATE and DELETE affecting existing rows. They do not protect
  against privileged trigger changes or `TRUNCATE TABLE`. The separate-identity smoke covers
  one scoped installer and an insert-only runtime; production identities and grants still
  need deployment-specific validation.
- SQL Server text columns do not receive tenant, actor, action, or target indexes. Applications
  must design any additional searchable columns and indexes for their workload.

The exact published PostgreSQL ecosystem baseline remains tenancy 0.15.0, audit-log 0.5.0, and
soft-delete 0.7.3. The packed-package ecosystem gate substitutes the audit-log 0.7.1 artifact and
published soft-delete 0.7.4 with strict peer dependencies; the checked-in baseline is unchanged.

## Performance verification

The [performance workflow](https://github.com/nestarc/nestjs-audit-log/actions/runs/40183158537)
passed, and the [benchmark documentation](../benchmarks.md#recorded-candidate-results--2026-10-25)
preserves the environment, artifact identities, every measured latency and all three PostgreSQL
executions. Each block used 50 warmups, 500 measurements and four repeats; concurrency was 1 or 4.

- PostgreSQL: 108,000 measured operations across three executions against published 0.7.0.
  No consistent broad regression reproduced across the executions, but hosted-runner variation
  was substantial. One run showed +24.45% in the small/concurrency-1 paired mean ratio, and the
  third showed +8.58% for large/concurrency-1. These results do not establish performance
  equivalence or exclude workload-specific regressions; retain the full comparison table.
  Large/concurrency-1 P99 and automatic create/delete P95 ratios increased in all three
  executions, so tail-latency behavior remains an unresolved observation for latency-sensitive use.
- SQL Server: 16,000 measured operations, 17,600 transactions including warmups and 8,800 audit
  rows. The median of four paired mean increments was +0.731 ms / +1.041 ms for small JSON at
  concurrency 1 / 4, and +44.939 ms / +44.296 ms for JSON occupying 128 KiB in NVARCHAR. Large
  payload cost was visible in all repeats. These are whole-transaction observations, not a
  production latency guarantee or a driver-only cost measurement.
- Correctness and cleanup passed for every measured block. The SQL Server data/log files did
  not grow during measurement. Different payload definitions and drivers prevent cross-database
  rankings. An application's latency budget still requires deployment-specific measurement.
